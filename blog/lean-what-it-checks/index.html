2026.11.24解説

Lean とは何か ―― 「Lean で検証済み」は何を確かめているのか

前の記事「AI はリーマン予想を解いたのか」では、「Lean で検証済み」という言葉が何度も出てきました。リーマン予想の証明を主張する1,700万行のコードも、Lean で書かれています。

この記事では、Lean とはどんな道具なのかを説明します。そのうえで「Lean で検証済み」と言うとき、何を確かめていて何を確かめていないのかを、コード例と図で整理します。

この記事のポイント

  • Lean は、数学の証明をプログラムとして書き、kernel という小さなプログラムに正しさを検査させる道具。
  • Lean が強く保証するのは「書いた証明が、書いた主張を正しく導いている」こと。
  • 「その主張が本当に言いたかったことか」と「なぜ正しいのか」は、人間が確かめるしかない。

この記事は2026年11月24日時点の情報です（Lean の最新版は v4.36.0）。Lean は月に1回ほど新しい版が出ていて、2026年は検査のしくみが大きく変わりました。

Lean はどんなソフトウェアか

Lean は、プログラミング言語であり、proof assistant（日本語では証明支援系）でもあります。proof assistant とは、数学の証明をコンピューターが読める形で書き、正しさを機械に検査させるソフトウェアです。

Lean は、Leonardo de Moura（レオナルド・デ・モウラ）が Microsoft Research 在籍中の2013年に作り始めました。いま広く使われている Lean 4 の正式版は2023年に出ています。開発の中心は、2023年に設立された非営利の組織 Lean FRO です。

数学の定義と定理は、Mathlib という共有ライブラリに集められています。2026年11月23日時点で、約14万の定義と約30万の定理が入っていて、772人が貢献しています。新しい証明を書く人は、この上に積み上げていきます。

コラム：Lean で形式化された主な成果

  • 2022年7月Liquid Tensor Experiment：数学者 Peter Scholze が2020年12月に出した挑戦。Clausen と Scholze の定理を、約1年半かけて Lean で形式化し終えた
  • 2024年7月AlphaProof（Google DeepMind）：Lean で証明を書くよう自分を訓練した AI。国際数学オリンピックで、ほかのシステムと合わせて6問中4問を解き、銀メダル相当の成績を出した。問題は人の手で Lean に訳した
  • 2026年8〜11月臨界線上の零点の割合（Anthropic）、準リーマン予想（OpenAI）、リーマン予想の主張（Alpöge と Claude）。どれも証明を Lean で書いている（前の記事）

証明をプログラムとして書く

Lean の中心にあるのは「命題は型、証明はその型の値」という考え方です。型のあるプログラミング言語を使ったことがあれば、次の対応表がわかりやすいと思います。

いちばん簡単な例を見てみます。

theorem two_add_two : 2 + 2 = 4 := rfl

「two_add_two という名前の定理を作る。主張は 2 + 2 = 4。証明は rfl」と読みます。rfl は「両辺を計算すると同じになる」という証明です。Lean は実際に計算して、両辺がどちらも 4 になることを確かめます。

次は、どんな自然数でも足す順番を入れ替えてよい、という定理です。

theorem my_add_comm (a b : Nat) : a + b = b + a := Nat.add_comm a b

「自然数 a と b について a + b = b + a。証明は、すでにある定理 Nat.add_comm に a と b を渡したもの」と読みます。関数に引数を渡すのと同じ書き方で、定理を使っています。

同じ定理は、次のようにも書けます。

theorem my_add_comm' (a b : Nat) : a + b = b + a := by
  omega

by の後ろには tactic を書きます。omega は、足し算と不等式だけでできた主張を自動で証明する tactic です。

用語：tactic とは

証明を組み立てる手順を指示する命令です。「ここは場合分けする」「この式を展開して整理する」といった操作を書くと、Lean が証明を作ってくれます。長い証明の大半は、tactic で書かれています。

コラム：「型」とは何か

プログラミング言語の型は、値の種類を表すラベルです。3 は自然数の型 Nat の値で、"abc" は文字列の型 String の値です。型検査は、関数に正しい種類の値が渡されているかをプログラムを動かす前に確かめます。

Lean の型はもっと表現力が高く、2 + 2 = 4 のような主張そのものを型として書けます。この型の値を1つでも作れれば、その主張は証明されたことになります。値を作れない型（たとえば 2 + 2 = 5）は、偽の主張にあたります。

このおかげで、証明の検査は型検査と同じ問題になります。型検査は機械的にできるので、コンピューターが証明を検査できるのです。

三平方の定理を Lean で証明する

もう少し実際の数学に近い例として、三平方の定理（ピタゴラスの定理）を Lean で扱ってみます。直角三角形で、直角をはさむ2辺の長さを a と b、斜辺の長さを c とすると a² + b² = c² が成り立つ、という定理です。

Lean で定理を扱う作業は、大きく3つに分かれます。数学の文を Lean の主張に書き直すこと、証明を書くこと、そして主張が意図どおりかを確かめることです。

手順1：数学の文を Lean の主張に書き直す

三平方の定理を、Lean のコードに書き直すと次のようになります。各行が数学の文のどの部分にあたるかを並べました。

書き直すときにいちばん注意が要るのは、前提と結論の部分です。ここに書いた内容こそが「Lean が証明したこと」になるからです。

手順2：証明を書く

三平方の定理は Mathlib にすでに入っているので、証明はその定理を使うだけで済みます。Mathlib は、Freek Wiedijk が選んだ「有名な定理100個」のうちどれを形式化したかを一覧にしています。三平方の定理はその4番目で、Joseph Myers が形式化しました。

Mathlib の三平方の定理は、「AC² = AB² + CB² であることと、角 ABC が直角であることは同値」という形で書かれています。図2の最後の行の .mpr は、この同値のうち「直角ならば」の向きを取り出すという意味です。平面に限らず、どんな次元の空間でも使える形になっています。

定理の長い名前を覚えておく必要はありません。証明を by exact? と書くと、Lean がいま証明したい主張に使える定理を Mathlib から探してくれます。約30万の定理がある Mathlib は、こうした検索と組み合わせて使うのが普通です。

こうして書いた証明は、elaborator が proof term に変換し、kernel が検査します。この流れは次の節で説明します。

手順3：主張が意図どおりかを確かめる

図2の主張を、わざと書き間違えてみます。Lean の反応は、間違いの種類によって大きく違います。

上の2つは、Lean が「証明できない」という形で教えてくれる間違いです。下の2つは、主張としては正しいので Lean が受理してしまいます。

3つ目の「直線にしてしまう」は、Mathlib の角度の約束によるものです。Mathlib では、長さ0の矢印との角を π/2 と決めています。そのため、A と B が同じ点のような「つぶれた三角形」でも、角 ABC は直角として扱われます。直線の上で角が直角になるのはこのつぶれた場合だけなので、直線版の定理は私たちが思い浮かべる直角三角形について何も言っていません。

このように、受理される間違いは主張を読む人間にしか見つけられません。この点は、次の節以降で見る「Lean で検証済み」の読み方の中心になります。

検査しているのは kernel という小さなプログラム

人が書いた Lean のコードは、そのまま検査されるわけではありません。まず elaborator と呼ばれる部分がコードを読み、tactic を実行して、proof term という細かな形に変換します。proof term は、使った推論をすべて省略せずに書き出したものです。

最後に、kernel がこの proof term を1つずつ検査します。Lean のリファレンスマニュアルは、kernel を「proof term を検査すること以外は何もしない最小の部品」と説明しています。

この分け方が Lean の設計の要です。tactic や elaborator は大きく複雑で、不具合があるかもしれません。それでも最後に kernel が proof term を検査するので、tactic の不具合が誤った証明を通すことはありません。信頼しなければならないのは小さな kernel だけ、というわけです。

Lean の開発者 de Moura は、2026年8月のブログで「elaborator は設計上、信頼しない部品だ」と書いています。そして、この分離こそが proof term を使う大きな利点だとしています。

コラム：Lean が前提にしている3つの公理

どんな数学も、証明なしに認める出発点（公理）を持っています。Lean の標準の公理は次の3つで、無矛盾であることが知られています。

  • propext：同値な2つの命題は等しい
  • Quot.sound：同じと見なした値は、割った後の型で等しい（商型）
  • Classical.choice：空でない型からは値を1つ選べる（選択公理）

注意が要るのは、ほかの「公理」が紛れ込む場合です。書きかけの証明に使う sorry は、sorryAx という公理として扱われます。これを使うと何でも証明できてしまいます。

計算をコンパイラに任せる native_decide も、使うたびに専用の公理を1つ足します。この公理は、kernel だけでなくコンパイラ全体が正しいことを前提にしています。どちらも #print axioms という命令で見つけられます。

「Lean で検証済み」を4つの問いに分けて読む

ここがこの記事でいちばん伝えたいところです。Lean のコミュニティでよく読まれているブログ Xena Project は、2026年11月12日の記事で「Lean で検証済み」という主張を読むための問いを4つ挙げています。順に見ていきます。

問い1：Lean で書いた主張は本当に言いたかったことか

これは Lean には確かめられません。リファレンスマニュアルも「Lean は主張が証明されたことは確かめられるが、それが意図した主張かどうかは確かめられない」と明記しています。主張を読んで、意図どおりかを判断するのは人間の仕事です。

たとえば次の定理は、Lean が問題なく受理します。

theorem rh_from_false (h : False) : RiemannHypothesis := h.elim

「偽の命題 False の証明 h が与えられたら、リーマン予想が成り立つ」という主張です。偽の前提からは何でも導けるので、これは正しい定理です。しかし前提の False は決して成り立たないので、リーマン予想について何も言っていません。こうした中身のない主張が、長い前提の中に紛れ込むことがあります。

定義の誤りも同じです。素数を次のように定義したとします。

def MyPrime (n : Nat) : Prop := ∀ m : Nat, m ∣ n → m = 1 ∨ m = n

「n を割り切る数は 1 か n だけ」という定義です。一見正しそうですが、この定義では 1 も「素数」になってしまいます。本来は「2 以上」という条件が要るからです。この定義で証明した素数の定理は、意図とは違う意味になります。

三平方の定理の図3で見た「空間を直線にしてしまう」「矛盾する前提を足す」も、同じ種類の問題です。

問い2：コンパイルできて未完成の部分が残っていないか

証明の途中を sorry で埋めると、Lean は警告を出しつつ先へ進みます。#print axioms を使うと、その定理が頼っている公理が一覧で出ます。

theorem rh_sorry : RiemannHypothesis := sorry

#print axioms rh_sorry
-- 'rh_sorry' depends on axioms: [sorryAx]

最後の行が Lean の出力です。sorryAx が出たら、どこかが未完成です。標準の3つの公理だけが出れば合格です。

もう1つの目安が、エディタに出る blue double check marks です。VS Code で Lean を書いていると、証明が通った定理の左側の余白に、blue double check marks（✓✓）が表示されます。これは「主張を Lean が読み取れて、kernel がその証明を受理した」という印です。リファレンスマニュアルは、普段使いならこのチェックを見れば十分だとしています。コマンドラインで lake build がエラーも警告もなく終わることも、同じ意味になります。

ただし注意点が1つあります。このチェックは、いま見ている定理の中の sorry は見つけますが、依存している別の定理の中の sorry までは見ません。リファレンスマニュアルもこの点をはっきり書いています。依存先まで確かめるには、上の #print axioms を使います。

問い3：主張した定理を本当に証明しているか

大きなプロジェクトでは、証明したい主張を「challenge file」に書き、信頼できる人が確認しておきます。lake comparator という道具は、challenge file の主張と実際に証明された定理が完全に同じかを照合します。標準の3つの公理だけを使っていることも同時に確かめます。名前は同じでも中身が少し違う定理にすり替わっていれば、ここで見つかります。

問い4：kernel の不具合を突いていないか

kernel もプログラムなので、不具合がありえます。そこで、別の人が別に作った kernel でも同じ proof term を検査し直します。lake check --paranoid（2026年10月の v4.35.0 から）は、公式の kernel のほかに4つの kernel で検査し直します。すべての kernel に同じ不具合がない限り、誤った証明は見つかります。

4つの問いと、よくある問題の関係を図にまとめました。図の上のボタンで問題を選ぶと、どの検査で見つかるかが表示されます。

図からわかるとおり、機械の検査をすべて通しても、「前提に False が入っている」「定義が間違っている」の2つは見つかりません。どちらも、主張の書き方の問題だからです。

kernel に不具合があったらどうなるか

これは仮定の話ではありません。2026年7月25日、AI の助けを借りて作られた、コラッツ予想を「反証」する Lean の証明が公開されました。sorry はどこにもなく、公式の kernel も受理していました。

実際には、入れ子になった型の扱いにある kernel の不具合を突いたものでした。7月28日にこの証明が小さな例に縮めて報告されると、Lean FRO は1時間後に修正を出しています。この不具合は、metaprogramming で kernel に直接宣言を送ったときにしか起きないものでした。de Moura は「実装の不具合であって、Lean の理論の穴ではない」と書いています。

この「反証」は、別の kernel である nanoda の古い版も通ってしまいました。nanoda にも別の不具合があったためです。つまり、2つの kernel にある2つの別々の不具合を同時に突く必要がありました。de Moura は、独立した kernel で検査し直す方法はいまも有効で、ただし両方を最新にしておく必要があるとまとめています。

この件のあと、OpenAI の研究者がサイバーセキュリティ向けの AI で協力し、kernel の別の誤りもいくつか見つかりました。すべて修正済みで、どれも nanoda は捕まえていました。AI が証明を書くだけでなく、検査器の穴を探す時代になっています。

コラム：検査器を検査する

kernel の不具合をなくすには、kernel そのものが正しいことを証明すればよい、という考え方があります。2026年10月、Lean に verified kernel が2つ同梱されました。

  • con-leche：Lean で書かれ、無矛盾であることが証明された初めての Lean の kernel。Claude（Anthropic の AI）が、Lean FRO の Joachim Breitner の厳しい監督の下で実装し、無矛盾性も証明した
  • con-ron：con-leche を Rust に訳し、元と同じ検査をすることを Aeneas という道具で証明したもの

ここでの「無矛盾」とは、con-leche が受理するものはすべて集合論の中に解釈を持つ、という意味です。それでも、使った集合論が無矛盾であることは前提として残ります。con-leche を動かすコンパイラに不具合がある可能性も残るので、別の言語で書いた con-ron でも検査します。

それでも残ること

Lean のリファレンスマニュアルは、comparator と複数の kernel を使っても残る前提として、次の3つを挙げています。

  • Lean の論理そのものが健全であること
  • 使ったすべての検査器に、同時に効く不具合がないこと
  • challenge file の主張の書き方に、人為的な誤りや誤解を招く書き方がないこと

3つ目は、問い1と同じです。そしてもう1つ、Lean の仕事の外にあることがあります。それは「なぜその定理が成り立つのか」を人間が理解することです。前の記事で見たとおり、リーマン予想の主張では、機械の検査はほぼ通っても、証明の中身を理解した人間はまだいません。

AI と Lean の組み合わせが広がっている

AI に証明を書かせると、もっともらしいのに間違った証明を出すことがあります。そこで、AI に Lean で証明を書かせ、kernel に検査させる組み合わせが広がりました。よく知られた例は2024年の AlphaProof です。2026年には、前の記事で見た3つの成果もすべてこの形をとっています。

2026年には、AI が kernel の不具合を探し、AI が verified kernel を書く段階にまで来ました。証明を書くことも、それを機械で検査することも、AI の助けで速くなっています。

その結果、もっとも時間のかかる作業は、主張が意図どおりかを人間の目で確かめることになりつつあります。AI の書く証明が増えるほど、問い1は重要になります。

おわりに

「Lean で検証済み」は、数学の世界でとても強い言葉です。それでも、その言葉が何を確かめたのかは分けて読む必要があります。

Lean の検証済みの証明に出会ったら、次の3つを確かめてみてください。

  • 主張と定義を書いたファイルを、誰が読んで確認したか
  • #print axioms の結果が標準の3つの公理だけか
  • どの検査器で確かめたか（公式の kernel だけか、--paranoid まで通したか）

私たちの新刊『言素 vol.1』の「AI for Science」の記事でも、AI による証明をどう検証してどう受け止めるかを考えています。あわせて読んでいただけるとうれしいです。
